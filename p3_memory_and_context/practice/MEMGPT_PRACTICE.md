# P3 补充实践：实现可观察的 MemGPT 式记忆循环

本任务接在 P3-01～05 的 RAG 实践之后。目标是亲手实现上下文组织、外部存储和事件驱动循环，不要求安装 MemGPT/Letta，也不以完整论文复现为目标。先用模拟模型检查协议，再用真实模型验证自主选择工具。预计额外 6–10 小时。

## 一、状态与存储（P3-06）

定义可序列化状态，并明确各部分的生命周期：

| 区域 | 内容 | 管理方式 |
| --- | --- | --- |
| system instructions | 记忆层级说明、工具 schema、控制流规则 | 应用固定提供，模型不可修改 |
| working context | 当前学习进度、有效时间预算、偏好、当前任务要点 | 大小受限，通过专用工具编辑；复用长期档案，不维护两份冲突的事实 |
| FIFO | 近期用户消息、助手调用、工具返回、系统事件；队首保留滚动摘要 | 队列管理器追加、压缩和移出 |
| recall storage | 完整历史消息，含已移出 FIFO 的消息 | 持久化、按用户过滤，支持关键词/时间检索与分页 |
| archival storage | 主动归档的学习记录、长笔记等 | 显式写入，使用 P3 检索能力读取 |

已有论文索引可作为知识检索来源，但用户的归档记忆必须与公共论文区分。所有私有数据以 user_id 隔离，历史同时记录 session_id。每条记录保留稳定 ID、来源和时间；数据放 artifacts/，不要写入源码目录。

实现 `init_memory(user_id, session_id, store)`：新用户初始化，老用户恢复 working context 和外部记录。新会话是否恢复旧 FIFO 必须明确记录；验收应包括 FIFO 为空但长期记忆仍可使用的情况。

## 二、队列管理与上下文预算（P3-07）

实现 `manage_context(state, event, **context)`：

1. 新事件转成消息，持久化到 recall，并追加 FIFO；读取历史时保留原消息 ID/时间，另生成检索返回消息，避免把旧事件误认为刚刚发生。
2. 按 system instructions → working context → FIFO 组装每次模型输入。实际 API 可使用多个 message，顺序和职责须保持一致。
3. 预算包含工具 schema、消息包装、working context、摘要及检索结果；为下一次工具返回和模型输出预留空间。使用 tokenizer 或显式标注保守估计，不把字符数称为实际 token。
4. 接近阈值时只发一次对应的 memory_pressure 警告，让模型有机会保存重要信息；达到硬上限时，由程序执行移出与摘要，不能依赖模型自觉遵守。
5. 按完整交互组移出，不能留下没有对应调用的 tool message。先持久化原文再移出；摘要同样有长度预算。
6. 单个工具结果过大时分页或返回可继续读取的记录 ID。如果固定区本身已无法容纳，返回 `context_overflow`，不截掉系统指令后继续运行。

警告阈值只是本实验配置，不是论文必须采用的百分比。记录移出前后大小、消息 ID、摘要及计数方式。

## 三、函数执行器（P3-08）

实现 `execute_memory_tool(call, state, **context)`，至少提供以下模型可见工具（名字可调整）：

| 工具 | 实际效果 | 返回结果的位置 |
| --- | --- | --- |
| working_context_update | 更新有效事实，保留旧版本、来源与更新时间 | 成功/失败反馈进入 FIFO |
| recall_search | 查询当前用户的完整历史，可分页 | 带原消息 ID 的搜索结果进入 FIFO |
| archival_insert | 将长笔记持久化到当前用户归档 | 新记录 ID 进入 FIFO |
| archival_search | 检索归档，返回可定位证据 | 检索结果进入 FIFO |
| send_message | 输出用户可见答复 | 记录在会话历史中 |

必须区分“工具造成的状态变化”和“工具返回消息”。检索结果不会自动进入 working context；模型需要另调编辑工具。

校验函数名、必填字段、类型、容量、页大小，错误作为关联 call_id 的工具结果返回，不终止整个进程。user_id 从 host 状态取得，不能由模型参数切换到别人的身份。原生调用必须保留调用 ID 与结果配对；支持一轮多调用或显式关闭并行调用。heartbeat 是 host 解释的控制参数，不传给数据库当查询字段。

## 四、控制流与链式调用（P3-09）

实现 `run_memory_agent(payload, **context)`，通过 P3 `run` 的 `mode="memgpt"` 分派。事件支持 user_message、timer 和 memory_pressure；timer 用显式注入的测试事件即可，无需创建后台定时服务。

```text
外部事件 → 更新 FIFO/检查预算 → 组装上下文 → 模型生成调用
                                              ↓
                                     校验并执行函数
                                              ↓
                                状态变化 + 返回结果进入 FIFO
                                              ↓
                    heartbeat=true：立即再次推理；否则 yield
```

`request_heartbeat=true` 请求工具完成后再推理一次。没有该请求则返回 `yielded`，等待新事件；不要用固定 while 循环无条件继续。yield 是调度状态，send_message 是用户输出，两者不能混同。最大轮数、总模型调用数、超时任一耗尽都返回明确状态。摘要模型调用也计入预算。

所谓中断在此实现为“事件触发下一轮处理”，不需要实现 token 生成中途的抢占。运行日志应区分外部事件触发与 heartbeat 触发。长任务进程崩溃后的逐步恢复属于 P5，不作为本补充任务要求。

## 五、固定演示与验收（P3-10）

先确定输入、预期存储终态和允许动作，再运行。每个场景保存执行轨迹、上下文快照和存储检查结果。

| 场景 | 输入与操作 | 验收证据 |
| --- | --- | --- |
| 偏好更新 | 先说每天 45 分钟，再改为 20 分钟 | 真实工具修改 working context；旧来源保留；计划使用 20 |
| 遗忘后召回 | 历史中记录“练习项目代号青鹭”，加入足够长的无关对话并触发移出，再问代号 | 查询前该细节不在 working context、摘要或 FIFO；recall_search 找到原消息，返回后才进入上下文 |
| 链式检索 | 分页结果第一页只有笔记 ID，下一次查询才能取得解释 | 至少两次调用；第二次参数使用第一次实际返回值；不需要用户说“继续” |
| 主动归档 | 要求保存一段过长学习笔记，随后检索其内容 | archival_insert 真正持久化；archival_search 返回原记录 ID |
| 压力与错误 | 注入 memory_pressure、非法参数和过大结果 | 有预算内输入、错误反馈、分页/拒绝和有限次数恢复，无死循环 |
| yield 与事件 | 某次调用不请求 heartbeat；随后注入 timer 事件 | yield 后模型调用计数不增长，timer 到来后才增加 |
| 重启与隔离 | 退出后另开进程恢复 A；再以 B 身份查询 | A 仍有新偏好；B 的检索及档案不含 A 的私有记录 |

“遗忘后召回”可先用固定状态快照保证细节确实在窗口外，再另跑端到端移出演示。若摘要仍含答案，该次只能证明摘要保留有效，不能计为外部召回成功。

对同一批输入比较：最近消息截断、摘要、摘要加检索，以及 MemGPT 式自主记忆循环。报告事实保留率、当前偏好正确率、证据有效性、峰值输入大小、模型/工具调用数、耗时与 usage。至少保存一条真实模型自主链式调用；模拟轨迹只证明协议和存储行为，不能替代自主决策验证。

最小展示用 CLI：每步打印事件、工具名与参数、working context 前后差异、FIFO 消息 ID、预算和 heartbeat/yield 状态。完整结果保存 JSONL；不记录密钥或要求模型输出隐藏思维过程。

## 与原始 RAG 论文的边界

本任务复用工程 RAG 作为 archival_search 的检索能力，不实现 RAG-Sequence/RAG-Token 的联合训练或概率边缘化。MemGPT 的价值演示在于“模型通过函数管理不同层级的记忆，并控制后续推理”，不能仅用一段静态档案拼进 prompt 就声称完成。
